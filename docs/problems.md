# カーネル問題調査報告書

このドキュメントでは、現在のOSカーネル実装において特定されたバグ、アーキテクチャ上の弱点、および安定性の問題についてまとめます。

## 1. メモリ管理

### 1.1 脆弱なページアロケータ (`page_alloc.c`)
- **メタデータの制限**: アロケータは、空きメモリ領域（ラン）を追跡するために固定サイズの `run_nodes` 配列（64エントリ）を使用しています。メモリの断片化が進むと、物理メモリに十分な空きがあってもこれらのノードが枯渇し、`PANIC` を引き起こす可能性があります。
- **同期の欠如**: アロケータの関数はスレッドセーフではありません。マルチコア環境では、並行したメモリ確保/解放によって競合状態が発生し、メモリ汚染を招く恐れがあります。

### 1.2 厳格なユーザーメモリ制限 (`process.c`)
- **固定ページマッピング**: `struct process` 内の `user_pages` 配列が固定サイズであるため、ユーザープロセスは128ページ（512KB）に制限されています。これにより、大規模なアプリケーションの実行が妨げられています。
- **静的な割り当て**: ユーザーページを追跡するためのメタデータがプロセス構造体に直接保持されており、たとえ使用されていなくてもカーネルメモリを消費し続けます。

## 2. プロセス管理

### 2.1 非効率なプロセスフォーク (`process.c`)
- **コピーオンライト (COW) の欠如**: `proc_fork` は、すべてのユーザーページを即座にディープコピーします。これにより、プロセス生成時のメモリ負荷とレイテンシが大幅に増加しています。
- **固定のプロセス数制限**: `PROC_MAX` が 8 に設定されているため、アイドルプロセスを除いて同時に 7 つのユーザープロセスしか存在できません。

### 2.2 基本的なスケジューラ (`sched.c`)
- **原始的なラウンドロビン**: スケジューラには、プロセスの優先度、リアルタイム制約、または効率的なブロッキング/ウェイクアップ機構のサポートがありません。
- **ビジーウェイトのリスク**: 高度なスリープ/ウェイクアッププリミティブが欠如しているため、I/O待ちのタスクにおいて非効率が発生する可能性があります。

## 3. ドライバ (VirtIO)

### 3.1 非効率なI/O完了待ち (`virtio_gpu.c`, `virtio_blk.c`)
- **スピンウェイト**: GPUおよびブロックドライバの両方で、コマンドの完了を検知するためにタイムアウト付きのスピンウェイト (`while (used_idx == used.idx)`) を使用しています。これはCPUサイクルを浪費し、ハードウェアが応答しなくなった場合にシステムハングを引き起こす可能性があります。
- **割り込みの欠如**: ドライバは完了通知にVirtIO割り込みを利用せず、手動のポーリングに依存しています。

### 3.2 限定的なハードウェア活用
- **単一のリクエストバッファ**: ブロックドライバは単一のグローバルなリクエスト構造体を使用しているため、並行したI/O操作を行うことができません。
- **小さなキューサイズ**: Virtqueueが非常に小さなサイズ（例：8記述子）で初期化されており、スループットが制限されています。

## 4. GUI & ウィンドウマネージャ (`wm.c`)

### 4.1 高い静的メモリ消費
- **巨大なウィンドウ構造体**: 8つのウィンドウスロットのそれぞれが大きな画像バッファ（~300KB）を保持しています。ウィンドウ用の静的メモリの合計は2.4MBを超えており、このカーネルの規模としては多大です。
- **静的なバックバッファ**: GPUドライバは大きな静的バックバッファを使用しており、さらにカーネルのメモリフットプリントを増大させています。

### 4.2 描画の非効率性
- **フルリドロー**: ウィンドウマネージャは「ダーティレクタ（更新領域）」最適化なしで全画面描画 (`wm_render_gpu`) を行います。毎フレーム、デスクトップ全体、すべてのウィンドウ、およびカーソルを再描画しています。
- **小さなイベントバッファ**: ウィンドウのイベントリングバッファは64エントリに制限されています。マウス移動などの頻繁な入力により、容易にイベントオーバーフローが発生する可能性があります。

## 5. 総合的な安定性とアーキテクチャ

### 5.1 `PANIC` の過剰な使用
- カーネルは、プロセススロットの枯渇やアロケータメタデータの不足など、致命的ではないリソース枯渇に対しても `PANIC` を使用しています。堅牢なカーネルであれば、ユーザーにエラーコードを返すか、適切に処理すべきです。

### 5.2 同期プリミティブの欠如
- カーネル全体でミューテックス、セマフォ、その他の同期プリミティブが一般的に欠如しており、将来的なマルチコア拡張に対して安全ではありません。

### 5.3 ユーザー/カーネルの境界
- ユーザー関連のコード（`user_init.c`, `user_wm_runtime.c` など）が現在 `kernel/` ディレクトリ内に配置されており、特権コードと非特権コードのアーキテクチャ上の境界が曖昧になっています。
